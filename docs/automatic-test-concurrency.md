# 自动测试并发设计与实测

## 结论与设置

自动测试点之间没有执行状态依赖：各点有独立 ASM、机器码、oracle、DUT 进程及用例证据。适合在资源有上限的前提下并发运行。

`co.test.concurrency` 默认 4，范围 1–8，设为 1 使用串行模式；设置在下次启动测试时生效。并发控制资源使用，不减少每点的指令数或检查项目。较大的并发量会增加同时运行的仿真进程、trace 和 CPU/内存开销，收益取决于机器与 DUT。

## 串行与并发的区别

| 项目 | 原串行执行 | 当前并发执行 |
| --- | --- | --- |
| 调度 | 等当前点完成再启动下一点 | 固定数量执行槽，空闲槽接下一个点 |
| P3–P6 生成 | 每轮一个随机点 | 每轮按并发量准备独立随机点 |
| P7 生成 | 每轮固定套件 | 保留同一套件，并发执行独立点 |
| 执行顺序 | GPR → 常规 → 特殊 | 保留这三个阶段的完成屏障，阶段内并发 |
| Icarus 文件 | 同工作区共享运行目录，整段串行 | 每槽独立 `code.txt`/cwd，内容相同的 TB 共享编译镜像 |
| Oracle | 一个懒启动 Worker | 复用原 Worker；请求按 ID 隔离，不增建 Worker 池 |
| 首失败 | 当前点失败后不启动下一点 | 首个观测到的失败停止派发，取消并等待在途任务退出 |
| 报告和清理 | 单点结果写入、轮末清理 | 结果/报告写入仍串行；整批退出后才清理和释放会话 |

并发时最先完成的失败点可能与串行最先遇到的失败点不同。已完成结果保留原编号和复现 ID；因取消结束的点不计入失败或错误统计。普通 GPR 基础检查仍每会话一次；P7 特殊压力点只能在常规点通过后启动。

## 编译与文件复用

- 不复制 RTL 工程。源码发现和现有内容校验缓存继续复用。
- 自动运行使用固定槽目录 `.co/iverilog/automatic/slot-N`。不同点只更新该槽必需的机器码；自动入口使用 `code.txt`，不受手动机器码路径覆盖影响。
- 相同私有 TB 内容映射到同一编译目录。短编译锁合并同时发生的冷编译，VVP 在锁外使用同一镜像并发运行。
- 每工作区最多 8 个共享编译目录，缓存最多保留 8 个工作区、每工作区 9 条记录（含手动运行）。缓存继续验证源码、include 解析和 VVP 内容；变化会触发重新编译。
- VVP 持有读租约，缓存失效或目录重用必须等待旧读者退出，避免替换仍在使用的镜像。不同 P7 刺激生成不同 TB 时仍需相应编译，不能冒充同一程序复用。
- `machineCodeInSim` 引用用例中已有的不可变机器码，不再把刚写入运行槽的相同内容复制回用例。每点保留重跑所需 TB 和结果证据，使用已有落盘 stdout 进行比较。

## 测量方法

`scripts/benchmark-course-test-concurrency.mjs` 使用真实 `runConcurrentCases`、`runCourseTraceCase`、内置 MIPS Worker 和 bundled Icarus，对同一批固定种子的最大 payload 用例比较 1/2/4 并发。仅 VS Code 外壳替换为真实文件系统适配器，没有模拟延时或替代 oracle/DUT。

每种并发量各测三次，轮换执行顺序；每次使用新的工作区与 Worker，包含冷编译、串行用例创建、汇编、oracle、DUT、比较和证据写入。RTL 复制只用于基准隔离，发生在计时前；payload 生成和额外 digest 校验也不计时。机器码及规范化 oracle/DUT trace 的摘要须跨全部样本一致。

并发量 1 是当前实现的串行对照组，执行顺序与原串行流程相同；不是对旧提交二进制另作计时。

测量不包含 VS Code UI、激活、通过用例留存清理和首次失败延迟，也不代表 P3 Logisim 或 P7 probe 的加速比。RSS 和 CPU 使用量仅统计 Node/Worker，不含 Icarus/VVP 子进程；总内存需要按实际工作负载观察。

## 2026-10-04 实测

环境：Windows x64（10.0.26200）、Intel i7-10870H（16 逻辑处理器）、约 15.78 GiB RAM，Node 24.15.0，bundled Icarus 13.0。使用本地 `gyc/P6/cpu` 真实课程 CPU，4 个固定随机种子，每点 4094 条 payload；没有裁剪为简化指令子集。每种并发量测三批，全部 36 次执行通过，机器码和规范化 oracle/DUT trace 摘要一致。

| 并发上限 | 四点耗时中位数 | 耗时范围 | 吞吐量 | 相对串行吞吐 | 每批编译次数 | Node/Worker 最大 RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 25.940 s | 24.278–31.383 s | 0.154 点/s | 1.00× | 1 | 311.4 MiB |
| 2 | 15.422 s | 15.393–17.549 s | 0.259 点/s | 1.68× | 1 | 343.4 MiB |
| 4 | 12.226 s | 10.263–12.804 s | 0.327 点/s | 2.12× | 1 | 388.1 MiB |

每批均为一次工具预检、一次编译和四次 VVP 执行，实际同时运行的 VVP 峰值分别为 1/2/4。VS Code 文件适配层累计写入约 1.322/1.328/1.340 MiB，增加量对应每个额外槽首次物化约 6 KiB 的私有 TB；其 copy 调用均为 0。这些文件计数不覆盖 Node 直接文件操作，不能解释为整个流程没有复制。

按用户选择，默认并发量为 4。实测中 4 并发吞吐提高约 112%，宿主 RSS 峰值约增加 77 MiB；资源紧张时可调为 2，该负载吞吐仍提高约 68%，宿主 RSS 峰值约增加 32 MiB。更高并发不保证线性收益，尤其 oracle 仍复用单 Worker，且每个仿真子进程也消耗 CPU 和内存。

完整本机证据保存在 `.co/benchmarks/course-test-concurrency.json`，包含全部样本、RTL 和编译产物哈希、实际指令集、随机种子、工具调用次数及结果摘要。该目录按仓库规则不提交；脚本可重新生成证据。证据明确区分基底提交和实际测试的未提交工作树构建。

复现方式（RTL 目录需自行提供）：

```powershell
npm run compile
node scripts/benchmark-course-test-concurrency.mjs --cpu-root 'E:\path\to\P6\cpu' --profile P6 --cases 4 --repeats 3 --output '.co\benchmarks\course-test-concurrency.json'
```
