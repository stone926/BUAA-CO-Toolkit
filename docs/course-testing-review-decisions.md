# 自动测试审查：待产品决策

本文只记录教程与 MIPS 规范无法唯一决定的产品行为。已有明确课程依据的问题直接在代码中修复，不列入此处。

## 1. 双方均为空的写回 Trace

### 问题

P4-P7 的现有对拍接口只观察 GRF/DM 写回。仅含 `nop`、未产生可见写回的正确程序，与完全没有执行程序的故障 CPU 都可能产生空 Trace；因此“双空即通过”会假阳性，“双空即失败”又会对前者假阴性。

当前行为：结果标记为 `error`，并明确说明“现有观测结果无法判定 CPU 是否实际执行了程序”，不会把不可判定结果冒充通过。

### 建议

推荐对内置生成器注入独立于待测指令集的、教程合法的可观察哨兵（例如一次确定的 GRF 写回），并在结果中单独标注该指令属于测试框架。对手选/外部 ASM，建议二选一：

1. 要求用例至少产生一次可观察写回，否则在运行前拒绝；
2. 扩展仿真接口，加入可验证的取指/宏观 PC 活性通道。

不建议将双方空 Trace 直接判为通过。

待确认：是否允许内置生成器在用户配置的指令集合之外注入框架哨兵；手选/外部 ASM 采用“拒绝不可观测用例”还是新增 PC 活性观测。

## 2. P7 probe 场景数小于完整覆盖下限

### 问题

`co.test.p7.probeScenarioCount` 同时像“硬上限”和“期望数量”。当配置值小于所有已启用中断/异常类别及其强制变体的数量时，不可能既遵守数量又完整覆盖；教程只规定应测语义，不规定该 UI 配置的优先级。

当前行为：严格遵守数量；容量足够时保证每类及其变体，容量不足时只能选择子集。默认值 64 足以容纳当前完整矩阵。

### 建议

推荐把该值定义为硬上限，并在低于当前启用功能的最小完整覆盖数时拒绝生成，同时报告所需最小值。这样不会静默扩容，也不会让用户误以为一次 probe 已完整覆盖。备选方案是把配置重命名为“最少场景数”，自动扩到完整矩阵。

待确认：选择“硬上限且不足时报错”，还是“最低数量且自动扩容”。

## 3. 手选/外部 ASM 的扩展指令集声明

### 问题

内置生成器支持在 P7 默认课程集合之外显式选择部分真实 MIPS 指令，并在生成文件中写入 `# instruction_set:` 元数据。若无条件信任该注释，任意手写 ASM 都可伪造白名单并绕过最终机器码 Profile 校验；若完全禁止，又无法表达合法的外部扩展测试意图。

当前行为：只有 case manifest 中不可由 ASM 内容自行声明的 `source.kind=builtin` 来源证明，配合内置生成器标记后，才能用该元数据扩展最终机器码白名单；手选/外部 ASM 即使伪造相同注释，仍严格按教程 Profile 默认集合校验。

### 建议

如产品需要外部扩展测试，增加不可由 ASM 内容自行伪造的显式配置或 case manifest 字段，例如 `allowedInstructions`，并仍限制在插件的 Profile 支持目录内。不要继续把普通源码注释当作授权边界。

待确认：是否需要支持手选/外部生成器的扩展指令集；若需要，采用工作区配置还是每个 case manifest 声明。

## 4. 手选/外部 ASM 的 MARS 原生步数预算

### 问题

教程要求 CPU 测试程序以永久自分支和延迟槽 `nop` 结束，但没有规定软件模拟器应再执行多少次自环后退出。不给修改版 MARS 原生 max-step 时，合法用例会一直运行并最终触发进程超时；固定过小的值又可能截断包含有界循环的手写程序。

当前行为：修改版 MARS 的 `coHalt=<pc>` 会在程序真实到达经 dump 验证的最终停机尾时立即成功，cliff exit、错误自环都不会冒充完成；`maxSteps` 只作为“到达停机尾之前”的安全预算。可信内置生成器按已知控制流和 payload 数量精确放宽；手选/外部 ASM 暂用 `max(65536, 64 * 最终机器码 words)`。这能覆盖默认 200us、4ns 周期测试台的 50000 个周期量级，但阈值并非教程规定。

### 建议

推荐新增显式的 `co.test.marsMaxSteps`（或按仿真时长计算的统一执行预算），并在报告中说明 MARS 是正常到达停机尾，还是在到达前耗尽预算。`coHalt` 已让两者可可靠区分，待决定的是用户是否应控制这个“合法长程序”的等待上限。

待确认：保留当前自动预算，还是改为用户配置/按仿真时长统一推导；“首次到达经验证停机自环”已由 `coHalt` 确定处理，不再属于待选项。
